# 四大 Agent 详细职责边界（草案，待确认）

> 对应 `plan.md §8.5` 前置条件「我确认各 Agent 的详细职责边界文档」。
> 本文件是 **草案**，供用户确认或修改；确认前不进入编排实现。
> 每个 Agent 均给出：职责 / 禁止事项 / 输入 / 输出 / 与现有模块映射 / 触发条件 / 验收标准。

---

## 总则（四端共享）

1. **职责分离、互不越界** — Interaction 不分析；Analysis 不直接与用户对话；Planning 不绕过 Interaction 推送内容；Story 不自行生成医学结论。
2. **分析先行、交互收口** — 所有面向用户的内容必须先通过 Analysis 结论一致性校验。
3. **可追溯链** — 每条输出可回溯到输入数据、推理路径、置信度。
4. **安全边界硬编码** — 不做诊断、不开处方、不替代医生、不制造恐慌，在编排层硬编码而非依赖 prompt。

---

## 1. 用户交互端 (Interaction Agent)

| 维度 | 内容 |
|---|---|
| **核心职责** | 管理对话节奏、语气、Persona；决定何时开口、说什么；处理 Message Burst / emoji 策略；把 Analysis/Planning/Story 的输出"翻译"成自然口语 |
| **禁止事项** | 自行给出医学结论或建议措辞；直接引用未经验证的原始数据；替 Analysis 下结论 |
| **输入** | 用户消息；Analysis 结论包；Planning 建议包；Story 叙事片段；Persona 配置 |
| **输出** | 面向用户的自然语言回复（含引用标注，如"根据近两周数据…"） |
| **现有模块映射** | `persona.py`、`ai_engine.py`（ResponsePlanner）、`psycho_engine.py` |
| **触发条件** | 用户发言 / 主动交互窗口命中（scheduler 触发） |
| **验收标准** | 回复语气与 Persona 一致；健康相关内容均带来源引用；不越界输出医学判断 |

## 2. 分析端 (Analysis Agent)

| 维度 | 内容 |
|---|---|
| **核心职责** | 从对话/数据中发现趋势、关联、异常；生成图谱洞察；更新 Routine；产出带置信度的结论包 |
| **禁止事项** | 单样本断言；过度推断；无数据来源的下结论；直接向用户输出 |
| **输入** | 结构化数据（health/routine/trajectory/feedback）；用户原始记录 |
| **输出** | 结论包 `AnalysisResult`（结论、数据来源、时间窗口、样本量、置信度、关联强度） |
| **现有模块映射** | `insights.py`、`routine.py`、`trajectory_graph.py`、`health_graph.py` |
| **触发条件** | 新数据写入后异步触发；用户显式询问分析时触发 |
| **验收标准** | 每条结论含来源+窗口+样本量；异常检测有阈值依据；无"单样本 → 规律"式结论 |

## 3. 计划生成端 (Planning Agent)

| 维度 | 内容 |
|---|---|
| **核心职责** | 基于用户主诉 + Routine + Persona + Profile Notes 生成推理树；给出 actionable 生活建议；动态调整计划 |
| **禁止事项** | 超出"生活方式干预"范围的医学建议；跳过推理树直接给"建议列表"；绕过 Interaction 推送 |
| **输入** | 用户主诉；Routine 画像；Persona；Analysis 结论包 |
| **输出** | 推理树（ReasoningNode）+ 叶子 actionable 建议（动作/时机/频率/时长/科学依据） |
| **现有模块映射** | `health_plan.py`（ReasoningNode + Expand API） |
| **触发条件** | 用户提出健康主诉；计划执行跟踪反馈；连续未执行需调整时 |
| **验收标准** | 建议带科学依据链；计划包含 3+ 类别、每类 2+ 条建议；不涉及诊断/处方 |

## 4. 故事生成端 (Story Agent)

| 维度 | 内容 |
|---|---|
| **核心职责** | 将结构化健康数据编织为可读的身体故事叙事（时间线叙事、周报总结） |
| **禁止事项** | 不可追溯的陈述；未标注置信度/样本量的关联描述；自行生成医学结论 |
| **输入** | Analysis 结论包；图谱事件/状态/轨迹；历史故事 |
| **输出** | 叙事文本（带来源引用与置信度标注），供 Interaction 包装后展示 |
| **现有模块映射** | `scheduled_stories.py`、`story_scheduler_daemon.py`、`index_story.html` |
| **触发条件** | 定时（周报/月报）；图谱事件里程碑 |
| **验收标准** | 叙事中的每个事实可回追溯到数据；关联处标注置信度；无未经验证的因果表述 |

## 7 项开放问题的推荐默认值（供确认）

> 对应 `plan.md §8.4`。每项给出推荐默认值 + 理由。用户可回复「全部采用推荐默认值」或逐项修改。

| # | 开放问题 | 推荐默认值 | 理由 |
|---|---|---|---|
| 1 | 通信协议与调度方式 | **同步 pipeline + 轻量事件通知** | 当前单机单进程、规模小；同步调用简单可测，事件通知（同进程回调）保持解耦。引入消息队列需新增依赖且收益小 |
| 2 | 安全校验层实现方式 | **混合方案（rule-based gate 为主 + LLM-as-judge 兜底）** | 硬规则（禁词/诊断词/处方词）用正则门快速拦截可解释、可测试；LLM-as-judge 兜底处理语义级越界（推荐词风） |
| 3 | 故事端与分析端协作 | **分析端先产出结论 → 故事端包装叙事** | 与编排原则 2「分析先行、交互收口」一致；避免故事端并行输出后难以合并、来源不可控 |
| 4 | 计划端与交互端衔接 | **下次聊天时注入 + 计划页可见，推送仅限高优先级** | 避免打扰（理念 7 零压力）；聊天注入自然，推送仅用于提醒类已确认事项 |
| 5 | 医学知识库引入范围 | **暂不引入大型知识库；内置"生活方式干预"白名单 + 科学依据模板库** | 范围克制、可维护；覆盖当前"生活方式干预"边界即可，超界一律拒答并引导就医 |
| 6 | 四大 Agent 实现方式 | **同一 LLM + 不同 system prompt（阶段一）** | 四端职责差异主要在 prompt 边界而非模型能力；独立 LLM 调用成本高且当前规模无必要。保留切换为独立调用的扩展点 |
| 7 | 编排层技术选型 | **plain Python 函数调度 + 轻量状态机（enum 步骤）** | 无新依赖、可测试、可逐步演进；LangGraph/CrewAI 在当前规模下过重。保留接口以便未来替换 |
